# Architecture decision 0004: Durable developer job state and scoped recovery

**Status:** Architecture approved by the project owner in [Issue #62](https://github.com/Snahdul/HaMi-AI-Engineering-Agent/issues/62#issuecomment-7140388694), 24 November 2026. Implementation and acceptance in progress. This is not a claim that recovery is available.
**Related:** [ADR-0001](0001-commandline-akka-isolated-coding.md), [ADR-0002](0002-development-logging-and-explicit-cli.md), [ADR-0003](0003-security-architecture-and-credential-isolation.md), roadmap #48, M4 #55/#58/#59 and #60/#61.

## Context

The M4 pilot demonstrated independently verified production generation and real draft publication. One earlier attempt produced an accepted candidate but failed publication; the CLI required a new authorized job to retry. The current publisher already has deterministic Git object identities and same-job ref/PR checks. The CLI generates a new ID on every invocation and writes a report before publication. The gate explicitly trusts the in-process coordinator report, not arbitrary imported JSON.

## Decision

- Keep Akka.Hosting and the existing job actor for bounded execution and retry. A Development host use case owns the lifecycle, local exclusive claim, checkpoint store and recovery orchestration. No automatic actor restart of external side effects, Akka.Persistence, cluster, database, or new privileged service.
- Use a strict versioned state record distinct from the report. Bind repository/issue, job ID, original base, parsed task digest, contract/scope/policy digests, publication capability, original result location, generation mode and budgets. State is private host metadata; no prompts, credentials or raw diagnostics. A verified evidence manifest binds the original host reports and artifacts. Hashes establish consistency, not authenticity against a compromised host or a process running with the same account.
- A canonical private local state root under one designated OS account, independent of checkout, results root and worktree root, is mandatory for production. Validate local filesystem, owner/ACL, path overlap, symlinks/reparse points and safe permissions before any claim. A caller-supplied temporary directory is permitted only at the internal test boundary; never as a production CLI override.
- One durable claim per canonical repository/issue and an exclusive process-held file handle; no lockfile unlink, timeout/PID-based takeover or distributed-lock claim. A released process lock does not remove a persisted claim. Initial v1 does not implicitly replace even terminal claims with a new job; explicit future operator policy is required. Unknown executing state blocks new starts and resume.
- Persist checkpoints before external side effects. Use a bounded strict JSON schema, monotonically increasing revisions, exclusive same-directory temporary file, flush and atomic rename; verify readback. Preserve ambiguous abandoned temporary data; fail closed until reconciled. This addresses process interruption, not a guarantee of power-loss durability.
- State transitions: Accepted -> Executing -> CandidateVerified -> PublicationPending -> Published. Failed, Exhausted, Cancelled, RecoveryBlocked and Published are terminal for execution. PublicationPending retains intent and consumed budget before external writes. CandidateVerified and PublicationPending are the only eligible publication-recovery stages; no automatic generation or guest restart. Report repair after Published cannot cause GitHub writes.
- A proposed publication-only CLI resume action accepts the original job ID, reviewed checkout, explicit draft authorization and original full base SHA. No free report import, issue/contract/model/scope/result overrides or optional issue journal/follow-ups for this recovery slice. New M5a jobs only; no migration or resumption of the historical M4 pilot. Revalidate current open owner-authored issue, active label, marker, canonical parsed task identity, reviewed policy/contract/scope, local and remote base, clean byte-identical checkout, evidence hashes, actual candidate and independent cleanup of every started MicroVM. Reuse the original deterministic gate, resolve the dedicated credential only after local acceptance.
- Reconcile remote effects by reading the existing job ref and PR and checking commit parent, entire tree, exact bytes, marker, redacted body and draft state. Reuse matching resources; create only missing authorized resources. Never overwrite a ref or modify an existing PR. Ambiguous effects, revoked authorization, stale base, conflict, unknown guest state and budget exhaustion block writes. No exactly-once transaction across the local filesystem and GitHub.
- Preserve budgets across process restarts. The initial proposed cap is three publication reservations (including the initial publication); the existing production contract allows two model attempts. Per-request/elapsed-time limits and read-only reconciliation behavior must be fixed before enabling recovery. No new model calls on resume. Rate-limit and uncertain responses remain pending rather than trigger unbounded retries.

## Implementation and evidence

M5a.1 introduces DevelopmentJobState, DevelopmentJobStateStore, DevelopmentJobStateRoot and offline tests. The root factory selects a fixed OS-account directory: Windows LocalApplicationData/HaMiDeveloperJobState-v1 on local NTFS/ReFS, with a protected inheritable ACL limited to the account, SYSTEM and local administrators; Linux local effective-UID account home/.hami-developer-job-state-v1 on ext2/ext3 (including ext4), XFS or Btrfs, with private 0700 directories/0600 files, ownership and regular-file link-count checks. Linux uses the local account database and fixed read-only /usr/bin/stat, without inheriting credentials; remote account databases and unsupported filesystems fail closed. Both paths reject overlap with results, checkout and worktree root and symlinks/reparse points. The root is not exposed as a CLI override. These are deliberately narrow host assumptions; OS administrators and same-account processes are trusted. Offline tests exercise permission checks in temporary directories, not real production root provisioning. A separate test-only process probe holds a claim, rejects competing processes, is forcibly terminated and verifies the retained claim; both CI jobs must execute it. Actual platform results and HaMi11 root provisioning still require verification. The state store remains an internal primitive: lifecycle integration, evidence manifest, CLI resume and remote reconciliation are still required. Do not treat its test-directory constructor or parsed state as a publication capability. No production path is activated by this increment.

M5a.1 follow-up: Linux build, format, offline state/root and cross-process crash regression succeeded on CI 45466669924; Windows build/format passed but the private-root test rejected an owner/ACL boundary. Windows token default owner need not equal the account user SID. New private files are now exclusively created using the existing .NET FileSystemAclExtensions.Create API, explicit user owner and protected allowlist ACL, verified through the new stream handle. Existing lock/state files are never repaired or overwritten to change permissions. Fixed, non-identifying failure classifications distinguish directory/file owner, canonicality and ACL failures. The exact original Windows failure condition is not yet proven; the original test remains mandatory. New Windows CI and actual HaMi11 provisioning remain open.

M5a.2 foundation: DevelopmentJobIdentityFactory binds the parsed task (canonical LF for host-generated goal line breaks only), exact reviewed Git contract/scope/policy bytes and original capability/budgets. It reuses the existing publication authorization gate and compares the raw local contract blobs with the approved base. This extends the byte-identical checkout condition to the three reviewed contract files. DevelopmentJobEvidence seals an immutable initial agent report and a bounded versioned manifest of SHA-256 hashes/relative artifact identities under the original job root. It checks the successful candidate with the existing in-process publication policy, correlates all executed attempts with their production/sandbox reports and actual worktree/snapshot/patch bytes, checks the accepted stdout and records the sandbox run IDs. Files are created exclusively and flushed; the private checkpoint must bind the manifest hash before publication. Hashes are not authorization in isolation. The new offline fixture tests correlation, altered source/stdout and unconfirmed prior cleanup; live read-only guest absence verification and reentry manifest verification remain outstanding. M5a.2 host integration (pending CI and HaMi11 acceptance): DevelopmentAgentCommand obtains the canonical issue lease after authorization and before allocating a job, creating a model client, starting Akka/MicroVM work or publishing any journal/PR. Draft-only production jobs persist Accepted then Executing, seal original evidence and commit CandidateVerified before publishing, persist a publication reservation before calling the publisher, and persist Published before updating the mutable atomic report projection. A known exhausted corrective budget with confirmed cleanup becomes terminal; uncertain failure/cancellation stays blocked. Existing non-recoverable issue-bound paths keep their original execution capabilities but acquire the same lease and create a minimal private `issue-N.legacy-active` marker before effects. Only the owning live process can clear its own exact marker after a passed or known exhausted outcome, confirmed cleanup, completed optional journal/publication and host shutdown. Interrupted or uncertain legacy jobs block new starts for that issue until manual reconciliation; no recovery capability is granted to those jobs. Non-issue execution does not acquire an issue lease. No real production run or publication is authorized by the implementation. Linux fix: UnixCreateMode applies only to CreateNew, never an existing lock opened with FileMode.Open. The previous Windows ACL/ownership and process probe passed on 6d1547c3; full current CI remains required. Report projection uses a separate exclusive temporary file and atomic rename; interrupted projections are preserved and future read-only report repair remains part of reentry. The same-issue claim remains after V1 terminal states. No change to the original publisher or actor authorization gates. M5a.3 implementation (pending CI and HaMi11 acceptance): the explicit action `development --repo <reviewed-checkout> --agent-resume <job-id> --publish-draft --publication-base <original-sha>` resolves only the fixed private registry (bounded scan of at most 1024 state records), then reacquires the canonical issue lease and re-reads the matching checkpoint. No caller-supplied issue, contract, results, model or source overrides. It rejects unknown/ambiguous IDs, corrupt registry entries and busy ownership. Accepted/Executing become RecoveryBlocked on explicit reentry; no model, actor host, build or new sandbox is started. For verified/pending/published states the private manifest hash is checked before deserializing the original report; the original report digest, attempt consumption and exact rebuilt manifest are checked against actual fixed artifacts. Published repairs the local report only and preserves an abandoned projection under .interrupted (no overwrite; conflicting preservation path blocks). For candidate/pending states re-fetch the approved issue, recompute task/contract/scope/policy identity, require unchanged base and explicit authorization, independently inspect every recorded sandbox with bounded read-only sbx inspect, repeat the existing candidate gate and recheck sealed evidence before reserving a publication attempt. The absence parser requires the exact named sandbox-not-found diagnostic (allowing whitespace wrapping and the fixed sbx ls hint), never just a nonzero exit or generic error. The historical HaMi11 diagnostic informs the parser; real runtime confirmation on HaMi11 is still required.

The publisher now reads the named ref and matching PRs before creating Git objects. Existing commit parent, complete tree, exact candidate blob, marker/message, author/committer/date, PR body/base/head/open/draft identity must match. Existing matching PR recovery performs no POST; a matching branch without a PR only creates the missing draft. A conflicting resource stops without writes. In the absence of a branch/PR, identical content-addressed Git object POSTs can be repeated by the same reserved job after an interrupted response; no claim of exactly-once across GitHub and the local store. Initial and resumed publication are bounded by three durable reservations total, at most 30 API requests and a four-minute cancellation budget per reservation (20 seconds per HTTP request; local Git checks retain their existing bounded deadlines). No blind branch/PR retry or ref update. No rate-limit sleep; failures preserve Pending. The original lost-PR-response fake transport test is retained and strengthened to require zero additional POSTs, with additional offline registry/manifest, parser override and report-repair tests. Remaining acceptance: complete fault matrix for other lost responses and conflicts, actual end-to-end lifecycle/reentry without model/guest execution, CI and real read-only sbx inspection on HaMi11. The current PR is not merge-ready. M5a.4 verifies Windows/Linux CI and separate HaMi11 acceptance. A real GitHub write test requires a separately authorized job. No automatic merge or weakening of ADR-0003; multi-step jobs and early-stage recovery remain later M5 work.
